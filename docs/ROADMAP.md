# Roadmap

Future ideas and planned improvements for the Amerikiosks website. Items are grouped by theme, not prioritized — move to a spec when ready to implement.

## SEO & Discoverability

- **`/llms-full.txt`** — `/llms.txt` is done and serving 200 in production (`src/app/llms.txt/route.ts`, covered by `tests/unit/app/llms.test.ts`). The full variant was never built, though an earlier version of this entry claimed both were. Decide whether it is still wanted: it is a second, much larger document to keep in sync with the site, and nothing has asked for it yet.
- **hreflang for translated slugs** — `generateMeta` emits `alternates.languages` only where both locales' paths are derivable without a lookup (machines routes, fixed paths like `/faq`). Pages, insights and projects are deliberately left out: their slugs are translated per locale, and the only resolver today is `PagesRepository.translateSlug()` — an HTTP call that covers `pages` alone, so calling it from `generateMetadata` would be the server hitting itself. A wrong hreflang is worse than none, hence the omission. Doing it properly means resolving the sibling-locale slug through the Local API at metadata time.

## Admin / CMS

- **Partner drag-to-reorder** — Replace the `order` number field with a drag-and-drop interface in admin. Requires a `PartnerOrder` Global or a custom Payload UI component.
- **Batch "Releases" + writer approval workflow** — Explored 2026-07-19, not committed. Two related asks from the client: (1) group several documents across collections into a named "release" with a message, publish/unpublish them together (~3-5 dev days: `Releases` collection + relationship + batch publish/unpublish hooks + custom admin UI); (2) writers can only save drafts, an approver actually publishes (~1-1.5 dev days: `reviewStatus` field + `access` control gate, no plugin covers this — Payload's Enterprise "Publishing Workflows" is approval/notifications-focused, not release-grouping). Reviewer "pending review" panel: per-collection filtered list view is free with the `reviewStatus` field; a unified cross-collection inbox is a custom admin view, +1 day. **Validate scope with the client once the full collection set is locked, not just for the first release — for the first complete project close-out.**
- **`docs/CLIENT-MANUAL.md` drift enforcement** — Checked 2026-07-24: the outline went untouched from 2026-07-20 21:27 (`b24b55c`) through 6 shipped feature PRs (async JotForm/Settings sync, ClaimForm wizard rebuild + R2 photo storage, customer-service UX polish, Form-fields DS migration, mega-menu/hero rework, Monday.com claims integration) before this check caught it. The two-speed policy in the top-level `CLAUDE.md` (bullet-per-iteration, full prose write-up only at project close) is still the right call — several of those blocks (ClaimForm, Support Hub) got rewritten mid-project, so full-detail sections would've needed rewriting twice. What's missing is enforcement: nothing currently prompts a manual-outline check at PR time. Add it as a checklist item in the PR template (or `/finishing-a-development-branch`) for any change touching a client-facing `/admin` workflow, rather than relying on remembering.
- **Generic multi-step/panel grouping for `src/blocks/Form`** — Raised 2026-07-24 while designing the kiosk-development/placement-application forms (`openspec/changes/kiosk-development-application/`, `openspec/changes/placement-application/`): both are long (12-16 fields) and render in the shared modal drawer (`CMSLink` `type: 'modal'` → `FormBlock`), which could feel cramped as one flat scroll. Deliberately deferred rather than bundled into either form's spec — it's a standalone UI feature (step navigation, per-step validation, progress indicator) that would affect every form using the generic drawer (Brand/Venue/Agency/Emerging-Brand/Start-a-Partnership too), not just these two. Ship both forms flat first; revisit step-grouping as its own design once real content is loaded and it's clear whether the flat drawer actually feels cramped, rather than guessing upfront. If built, would likely need a per-field "step" grouping config on the `Form` doc (mirrors the `externalId` per-field override pattern from the sync-integration work) and a stepper UI in `FormBlock`/the drawer, closer to `ClaimForm`'s wizard than a full rebuild.

## Infrastructure

- **Expand-contract for destructive migrations — the real fix for the v1.38.0 outage.** The release took the home page and `/contact` down for ~90 seconds with `column pages__blocks_formBlock.intro_content does not exist`: `migrate` had already moved the Form block's panel columns into a `_locales` table and dropped the originals, while the **old build was still serving traffic**. `/machines` stayed up only because it carries no form block. The workflow's own comment had assumed "reads survive that" — they do not. PR #191 is the safety net (close the public site during the window, but only when the release actually drops or renames something); the fix that removes the window entirely is expand-contract: one release adds the new structure and backfills while keeping the old columns, a later one drops them once the new build is live. Payload's generated migrations always bundle the `DROP`, so this means hand-editing them to defer it, and it costs an extra release per localization change. Worth it for blocks that appear on high-traffic pages; the maintenance page covers everything else.
- **Create the `maintenance-site` firewall rule in Vercel** — PR #191 enables it during a destructive migration, but the rule is created by hand in the dashboard like `maintenance-admin`/`maintenance-api`, and **until it exists the PR is inert** (the step is `|| true` with a warning, deliberately, so a missing rule never fails a release). It should answer **503 with `Retry-After`** and serve `public/maintenance.html` — not 403 and not 500. A 5xx that looks permanent is what gets pages dropped from the index.
- **`llms.txt` + markdown pages** — Payload-driven markdown pages served at known URLs (e.g. `/about.md`, `/services.md`) for AI agent consumption, following the `llms.txt` spec.
- **Convert `[locale]/[slug]/page.tsx` to a catch-all (`[...slug]`)** — `nestedDocsPlugin` is already active on `pages`, but setting a `parent` on a doc only affects breadcrumbs/SEO `generateURL` metadata, not actual Next.js routing: the App Router resolves URLs purely by folder structure, and `[slug]` only matches a single segment. Any page nested under another (e.g. `/customer-service/request-a-refund`) needs its own bespoke route folder today (see that page's route for the current workaround). Converting to `[...slug]` would make nested pages "just work" without a dedicated folder per case, but touches routing for every page on the site: `generateStaticParams` would need to build full breadcrumb paths instead of a single slug, `queryPageBySlug` would need to match a joined path (likely via a denormalized `fullPath` field kept in sync by a hook) instead of `where: { slug: { equals } }`, the `home` special case (`slug === 'home'` → `/`) needs adapting to an empty array, and `PayloadRedirects`/`translate-slug`/the SEO plugin's `generateURL` all currently assume a flat single-segment slug and would need auditing. Worth doing once there's a second/third nested-page case, but deserves its own reviewed plan rather than being bundled into unrelated feature work.
  - **Analyze whether `nestedDocsPlugin` itself could resolve this more directly** before building the catch-all migration by hand — worth a spec-first look at whether the plugin already exposes (or could be configured to expose) the joined path in a form `generateStaticParams`/`queryPageBySlug` could consume directly, instead of us hand-rolling a `fullPath` denormalization hook from scratch.
- **shadcn primitives → DS migration** — `Select` was already replaced with a native `<select>` (real bug: Radix portals to `document.body`, which sits below a native-popover drawer's top-layer). The rest (`Button`, `Input`, `Label`, `Checkbox`, `Textarea`, `Pagination` in `src/components/ui/`) are still shadcn wrappers with no active bug — migrate to `ds.bepartnerlabs.com` components when there's a dedicated pass for it, not bundled into unrelated feature work.
- **Pending major dep bumps — investigated 2026-07-21, both genuinely blocked (not env flakiness):**
  - **`typescript` 6→7** — attempted on `chore/upgrade-typescript-7`. `tsc --noEmit` fails immediately under TS7 because it removed the `baseUrl` compiler option. Vitest doesn't catch this (it type-strips via esbuild, no real typecheck) — `pnpm test:int` passes even when the project doesn't actually compile, so don't use test results alone as a green light for TS bumps. Fixed the *config-level* half of this: dropped `baseUrl` (paths already resolve relative to `tsconfig.json` without it), fixed 4 files with bare `src/...` imports that only worked via `baseUrl` (`src/blocks/Banner/Component.tsx`, `src/collections/Insights/hooks/populateAuthors.ts`, `src/heros/PostHero/index.tsx`, `src/utilities/getDocument.ts`), and fixed 2 real generic-type regressions in `src/utilities/getDocument.ts`/`getGlobals.ts` (were hand-rolling `keyof Config['collections']`/`keyof Config['globals']`, which TS7 widens to `string | number | symbol` — switched to Payload's own exported `CollectionSlug`/`GlobalSlug` types instead, which is more correct regardless of TS version). With all of that, `tsc --noEmit` passes clean under TS7 — but `pnpm build` still fails: Next.js 16.2.10's own build-time TypeScript version detection doesn't understand TS7 and crashes with `The "id" argument must be of type string. Received undefined` after trying to reinstall `typescript`. This is a Next.js-side gap, not fixable from this repo — retry once Next.js ships TS7 support. The tsconfig/import/type fixes above are harmless under TS6 too and worth keeping regardless.
  - **`@vitejs/plugin-react` 4→6** — hard startup failure, `ERR_PACKAGE_PATH_NOT_EXPORTED` on `vite/internal` when vitest loads its config; the installed `vite@7.3.6` (pulled in transitively by vitest) doesn't expose the subpath plugin-react 6 imports. Reproduced twice in isolation, not a fluke. Needs a compatible `vite`/`vitest` pairing investigated before retrying.
  - **`graphql` 16→17** — do not attempt: `payload` and `@payloadcms/next` both pin `"graphql": "^16.8.1"` as a hard peer dependency. Blocked until Payload ships v17 support.
  - Also learned: this repo's local dev DB runs via Podman (`podman-compose up -d`, needs `podman machine start` first if the VM isn't running) — `tests/int/redirects.int.spec.ts` needs a real Postgres connection and will fail/timeout with a misleading "hook timed out" error if the machine isn't up. Check `podman-compose ps` before blaming a dependency bump for integration test failures.

## Testing

- **Migration safety check for forms is now a script.** `./scripts/verify-forms-migration.sh [--round-trip]` snapshots every form, field, label, select option and Form-block panel value straight from Postgres, applies the pending migrations, and compares *semantically* (these migrations move columns into `_locales` tables, so a raw table diff reports differences by design). Run it on a production restore — a fresh local database has nothing to lose and passes regardless. It is what caught the `value_type` backfill gap.
  - **Used for real before v1.38.0** (2026-07-30) against a production restore, `--round-trip`: 13 pending migrations, all touching form tables, applied → reverted → re-applied with *no form, field, label, option or panel value lost*, and the data intact afterwards (4 forms, 14 submissions, 177 submission-data rows, 29 claims).
  - **`migrate:down` is not a rollback for the forms migrations — it is data loss.** Found 2026-07-30 running `--round-trip` on a fresh production restore: 10 losses, none of them caused by the migration under test. `requires_consent` fell back to `false` on all four forms (from `20260728_192449_forms_consent_and_turnstile`) and the six `autocomplete` values on Design Your Kiosk were wiped. The cause is inherent rather than a bug: those `down` functions `DROP COLUMN`, so re-applying `up` recreates the column empty. Forward-only was clean on the same run. So a failed release is recovered by rolling *forward*, or from a dump — never by walking these migrations back down.
  - **And it still did not prevent the outage** — worth writing down, because the script gives a false sense of coverage. It answers "does this migration lose data?", not "can the currently-deployed build still read the schema this migration produces?". Those are different questions and the second one is what took the site down. A check for it would apply the migrations to a restore and then run the **previous** build against it; until that exists, treat any migration containing a `DROP`/`RENAME` as needing the maintenance window regardless of what this script says.

- **The e2e suite does not run in CI, and only passes against a seeded database.** Checked 2026-07-28 while shipping `feat/forms-hardening-and-ux`. `.github/workflows/ci.yml` runs `pnpm test:coverage`, which is vitest only — the 23 Playwright tests in `tests/e2e/` never run on a PR. They only run locally via `pnpm test` (which chains `test:int && test:e2e`), and there they are fragile for two independent reasons:
  - **They assume seeded content.** Restoring a production dump to debug something makes 5 of them fail: `admin.e2e` logs in as `dev@payloadcms.com` (`tests/helpers/seedUser.ts`), which does not exist in real data; `customer-service.e2e` picks the first brand radio, whose set differs; and `frontend.e2e` asserts the header CTA is `<a href="/start-a-partnership">Start a Partnership</a>`, but that CTA has been `type: 'modal'` (a `<button>`) since PR #94 — a test that breaks when an editor legitimately changes content is anti-signal.
  - **`playwright.config.ts` starts `pnpm dev` with `reuseExistingServer: true`.** Against a dev server, `<nextjs-portal>` (the error/dev overlay) intercepts Playwright's clicks: 3 further failures that vanish entirely when the same suite runs against `next start`. Measured — 8 failures on `pnpm dev`, 5 on a production build.
- **Decide what the suite is for before investing in it.** The tests worth the cost are the ones that protect something legally or physically consequential and cannot be expressed as a unit test: the GA4 consent gate (`consent-banner.e2e`, and the client has had a lawsuit), the accessibility widget's real computed styles and persistence, and `customer-service.e2e`'s check that the URL printed on physical kiosk QR codes still resolves. The ones that earn nothing: `admin.e2e` (3 tests navigating Payload's own admin panel — Payload tests that, we do not), and the CSS-assertion smoke tests in `frontend.e2e` (`header has dark background`). If the suite stays, it should run in CI against `next start` with its own seeded database, and its assertions should be content-agnostic (roles and structure, not specific labels an editor owns).

## Forms

- **A BPL form-builder plugin of our own** — Decided 2026-07-29 while hardening this project's forms. `@payloadcms/plugin-form-builder` got us a long way, but we ended up bolting a lot onto it through `formOverrides`: per-field Monday column ids, a declared "value type" (text/phone/website) because the plugin has no phone field, an `autocomplete` select, a consent toggle with its own stored record, `description`/`footnote`/structured confirmation fields, and two field types the plugin ships but does not enable (`radio`, `date`) plus one it does not have at all (`toggle`). Two smells say this belongs in a plugin rather than in overrides: we mutate the plugin's *shared* block objects to add fields (which broke Payload's boot with `DuplicateFieldName` until an `addOnce` guard went in — the objects are reused across config evaluations), and the upload block's `mimeTypes` is free text, so a typo silently disables the filter. Worth packaging alongside `bpl-ds` once a second client needs forms, not before.
- **Multi-step forms, derived from the flat field array (not a nested block).** Three of the five forms have **16 fields** and *Placement Application* has **10 required** — in the drawer that is a screenful of scroll above the submit, which is why that button had to become sticky. Worth splitting into steps. What is *not* worth it is the obvious shape, a container block holding fields: the whole pipeline assumes `form.fields` is flat (`validateSubmission`, the route's `unknownField` check, `buildColumnValues`' name→externalId map, the admin columns-reference panel, the progress bar, the error summary), and every one of those is a place where a nested field can drop out of the Monday sync *without anything visibly failing* — the worst failure mode for a lead channel. Instead treat a marker in the flat array as a step boundary: the `message` block already acts as a visual section separator in the drawer (`.ak-form__message-block`), so either promote it or add a minimal `stepBreak` with a title. Zero changes to the route, validation, sync or column mapping; a form with no separators stays single-page, so no content migration. The real work is client-side: validate only the current step (`trigger(fieldsOfStep)`), move focus to the step heading on advance, survive the browser back button, and **not lose answers on reload** — a step form that empties itself is worse than a long one, which means a `sessionStorage` draft and its own privacy decision (personal data at rest in the browser). Pays for itself twice: a stepper ("step 2 of 4", `aria-current="step"`, replacing today's required-field progress bar) and per-step drop-off analytics, which is the only thing that tells us *which* field to delete.
- **Re-syncing a submission creates a duplicate Monday item.** `syncFormSubmission` always calls `create_item`, so the Resync button in /admin — whose whole purpose is the `syncStatus: 'error'` case — files a *second* item whenever the first one was created and something later failed (the realistic case being an attachment Monday rejected). Now that `externalItemId` is persisted the moment the item exists, the fix is available: when it is already set, update that item's columns (`change_multiple_column_values`) and retry only the file, instead of creating. Small but it needs a new repository method and its own tests, so it did not belong in the hardening PR. Observed live: resyncing a submission whose file was rejected produced items 12667673959 and 12667682604 for the same lead.
- **A `location` field backed by Google Places, proxied server-side.** Better than the cascading selects below for the case that actually matters here: *Placement Application* asks where the kiosk goes, and one validated address beats country → state → city both for the visitor (one field) and for the data (no "Main St" garbage). It also lands somewhere real: Monday's `location` column takes `{lat, lng, address}`, verified working in `docs/monday-column-types.md`, so a Places result maps onto it exactly — and the address components carry the ISO code + country name pair that the `country` column needs. Three design points, in order of importance. **(1) Proxy it, don't embed it.** A browser-side Places widget means a public API key and Google's Maps JS on a marketing page — a third-party script with its own privacy/consent implications, plus a key that bots can bill against. Instead: our own ARIA combobox (debounced) talking to `/next/places/autocomplete` + `/next/places/details` behind the repository pattern, with the key read server-side from Settings under the same authenticated field access as `mondayApiToken`. The route's existing rate limiter then covers the cost risk for free. **(2) Re-verify server-side.** Store and trust the `place_id`, and resolve details on the server at submit time; otherwise "only selectable from the dropdown" is a client-side fiction and `curl` posts anything. **(3) Never block a lead on Google.** If the API is down or over quota the field must degrade to accepting plain text, the same call we made for Turnstile when Cloudflare is unreachable. Before building, check Google's caching terms: `place_id` is storable indefinitely, other Place fields have a limited cache window, and a lead record kept for years is exactly the case that rule is about.
- **Data-driven select options (and dependent selects), instead of hand-typed label/value pairs.** (For addresses specifically, prefer the Places-backed `location` field above; this entry is for the general case — machine models, industries, anything the client curates.) Today every `select`/`radio` carries its options in the form document, and the plugin's builtin `country` (full ISO list) and `state` (US only, and *not* filtered by the chosen country) are the workaround. A field whose options come from a named dataset would replace both and open up country → state → city cascades. Two constraints decide the design. **(1) The server must resolve the same source.** Validation currently checks the submitted value against the `options` in the form doc; with a remote source the route has to resolve the identical set server-side, or a select silently degrades into a free-text field for anyone with `curl` — and for a cascade it must validate the *combination* (that the state belongs to the country), otherwise the board fills with inconsistent leads. **(2) Size decides where the data lives.** Countries + US states is a bundled static module (~100-300kB, and the shared module is what makes server-side validation free); worldwide cities is tens of MB and must be fetched on demand through a `/next/options/[set]` route behind the repository pattern (`ApiClient` → `OptionsRepository`), never bundled. A concrete win beyond convenience: a dataset-backed country field knows both the ISO code *and* the name, which is exactly the `{countryCode, countryName}` pair Monday's `country` column requires and which `docs/monday-column-types.md` currently lists as impossible to produce. One caveat to design around: pointing a 200-option field at a Monday **dropdown** column with `create_labels_if_missing` would pollute the board with labels — those belong in a `text` or `country` column. Client-side cost is the usual dependent-select work: reset children when the parent changes, loading state, and announcing the change to screen readers.
- **Rich text / markdown as a *respondent* field type — discarded 2026-07-30.** Not for effort reasons: there is nowhere for the formatting to go. Verified against the live Monday API — `long_text` stores plain text (newlines survive, nothing else), and `doc` (Monday Docs) accepts the write and stores nothing, so any formatting the visitor produces is flattened before it reaches the board: the sales team would read `**urgent**` and `- item` as literal noise in a cell. On top of that, a Lexical editor is ~100kB+ of JS on a marketing page whose job is to convert (the frontend currently ships only Lexical's *converters*, not the editor), it is worse to fill on a phone than a plain textarea, and it adds sanitisation surface plus a link-spam vector. The textarea with a character counter already covers "long answer". If the real need reappears, the cheap answers are: split the prose into concrete fields (better data and a better sync), or use the existing `upload` field for a formatted document. Rich text stays where it belongs — the admin side (intro, consent text, confirmation, footnote), which is already localized richText.
- **Direct browser → R2 upload for form attachments** — Not worth it today, with the numbers to say so. Attachments currently go browser → our `/next/form-submissions` route → private R2 bucket, capped at 8MB. Measured 2026-07-29: the three Monday boards hold **234 leads total since 2023** (112 + 24 + 98), i.e. ~6-7 a month across every form, of which only two forms even have an attachment field and it is optional — call it 2-5 uploads a month, so under ~40MB/month in the worst case against a 1TB allowance. Vercel bills active CPU, and streaming a file is I/O wait rather than compute, so this is not the shape of work that drives the bill; the real cost risk was always *volume*, and that is what the rate limit, honeypot and Turnstile now cover. Going direct would also cost three new problems: CORS on the private bucket, validating that a submitted object key actually belongs to that submitter, and cleaning up files uploaded but never submitted — and it would lose the ability to reject a file *before* it exists (today a PDF renamed to .jpg is refused without ever touching R2). **Revisit if the forms ever accept video** (a phone clip is 100-300MB, which hits the function's request-body limit, not the bill) **or if volume grows by ~100x**; that is also when resumable multipart upload starts paying for itself.

## Audit backlog (2026-07-30)

From a full read-only audit of `main` before v1.38.0. The critical and high findings shipped in #182–#191; what follows is what was deliberately **not** fixed then, so it does not evaporate with the session that found it. None is urgent on its own.

- **`add_file_to_column` interpolates into the GraphQL query string** (`GenericMondayRepository`, `MondayRepository`) while `create_item` correctly uses variables. Not attacker-reachable today — the values come from Monday's own response and admin-configured column ids — but it is the one place that would bite if a caller ever passed user input.
- **Media uploads are only type-checked on a path this project does not use.** `Media.mimeTypes` plus a `beforeValidate` gate now stop a disallowed file from becoming a document, but neither can stop the *upload*: `clientUploads: true` has the browser PUT straight to R2 through a presigned URL, and that handler's `access` hook is called with `{ collectionSlug, req }` only — it never sees the mime type, so there is no seam to validate in (verified in `@payloadcms/storage-s3/dist/generateSignedURL.js`). An editor account can therefore park an SVG or HTML file on the CDN host at a key it chooses, whether or not the document create then fails. Closing it is an R2-side job: a content-type policy on the bucket, or `Content-Disposition: attachment` plus a restrictive CSP on the CDN hostname. Blast radius is smaller than it first looks — the CDN is a separate origin from the site and admin, and Payload's auth cookie is host-only — so this is phishing-on-a-trusted-domain rather than session theft. Not fixable from this repo; needs someone with Cloudflare access.
- **`syncClaim` triggers the job with an un-awaited `fetch` and no `waitUntil`** — on Vercel the function can freeze once the response is sent, so the trigger may never fire and the claim sits at `syncStatus: 'pending'` until someone resyncs by hand. Also sends `Bearer undefined` when `CRON_SECRET` is unset.
- **Bulk resync fetches every errored doc with `limit: 0` and processes them sequentially** (both Claims and FormSubmissions), each with a Monday round-trip and, for submissions, an R2 download per attachment. A large backlog hits the function timeout mid-run.
- **`proxy.ts`'s matcher exclusions are unanchored prefixes** — a future slug starting with `admin`/`api`/`next` (say `/next-generation`) would silently skip i18n and redirect middleware.
- **Env hygiene** — `environment.d.ts` declares 4 of the ~14 vars actually read; `.env.example` lists `ODOO_ENDPOINT` and `JOTFORM_API_KEY` that nothing reads, and omits `MONDAY_API_TOKEN`; production and preview address R2 with different `S3_ENDPOINT` shapes, with no comment saying why.
- **Content, not code:** several documents have empty SEO fields (e.g. `/insights/end-to-end-operation` renders `<title>Amerikiosks</title>` because `meta.title` is blank). Worth a sweep in `/admin` once someone owns the copy.

### Not a bug, documented so nobody re-investigates it

The admin's SEO fields can crash with React's "Maximum update depth exceeded" — nine experiments narrowed it to the plugin's character-count indicators re-rendering per keystroke, and **only under a burst of keystrokes with no pause**, which is what automation produces. Normal typing and pasting are both fine, the main Title field never fails, and it reproduces on `d94ef70` (before any of this work). Autosave was the obvious suspect and was **ruled out** — it still happens with autosave switched off entirely. Full log in `docs/qa/`.

## Design System

- **Where the social icons belong — footer only, or header too, or a pre-header?** Raised 2026-07-30 while making the footer fully translatable, deferred on purpose. `SocialLinks` (`src/components/SocialLinks/index.tsx`) is one component rendered in three places via a `variant` prop: `footer`, `header` and `mobile`. That is a design question, not a code one — the component already supports any answer, so nothing needs building until the call is made. Three things to weigh. **(1)** Social icons in the main header compete with the nav and the CTA for the most valuable strip of the page, on a B2B site whose header's job is to move people toward a form; sending them to Instagram from there is a leak, not a conversion. **(2)** A pre-header (thin bar above the nav) is the conventional home for exactly this — secondary links that should be reachable but not prominent — and it could also carry the language switcher and the contact email, which would take pressure off the main header. But it is one more full-width band on mobile, where vertical space is already the constraint. **(3)** Footer-only is the safest default and costs nothing to try: `data-ga-section` is already set per variant (`social_link_click` with `header`/`footer`/`mobile`), so the click data to decide this empirically is being collected right now — check whether the header icons get any clicks at all before designing a new band to hold them.

- **Narrow "prose" lane on `.bp-content-grid`** — Discussed 2026-07-20 while building the legal pages (Privacy/Cookie/Terms). `.bp-content-grid` (`src/app/(frontend)/globals.css`) currently exposes `full-width` / `breakout` / `content` named lines, with `content` maxing out at 1344px — fine for marketing layouts (cards, heroes) but too wide for a wall of body text (blog posts, legal pages), where comfortable line length is closer to ~44rem. Shipped a stopgap for now: `max-width: 44rem; margin-inline: auto;` scoped to `.ak-content .ak-rich-text` in `src/blocks/Content/styles.css` — narrows the *text*, not the grid. The more correct fix is a new named line on the shared grid itself (e.g. `[prose-start]...[prose-end]`, narrower than `content`) so blog/legal content can opt in via `grid-column: prose`, consistent with how `breakout`/`full-width` already work. Deliberately not done in the GDPR branch — it touches a primitive shared by every block on the site and belongs in its own design-system spec (`openspec/specs/design-system/spec.md`), not bundled into unrelated feature work.

## Analytics

- ~~**TrustStrip dwell time dashboard**~~ — **dropped 2026-07-30, the metric had no signal.** The plan was a report of which partner logos get the most screen time. They all get the same: the strip is an autoplaying marquee, so a logo is on screen for exactly as long as the animation takes, and "dwell" measured the CSS rather than the visitor. Meanwhile `partner_logo_dwell` had reached **10,385 events — 80.4% of everything in the property**, against 977 `page_view`, which is close to GA4's per-session event limits and drowns every aggregate view. Replaced by a single `trust_strip_dwell` per page view (`dwell_seconds`, `partner_count`), which answers the only question that was ever real: was the section seen, and for how long. Historical `partner_logo_dwell` data cannot be deleted from GA4 — date-scope any report to after this ships.
- **Mark `generate_lead` and `claim_submit` as GA4 Key Events** — manual step in GA4 Admin → Events → toggle "Mark as key event". Code already fires both (declarative `data-ga-event` + synthetic-click pattern); `form_start`/`form_submit` are separately auto-collected by GA4 Enhanced Measurement, no code needed for those.
- **Register the event parameters as GA4 custom dimensions, or the leads board cannot segment.** `GAListener` already sends `form_name`, `block`, `section`, `label` and `machine_id` alongside each event (`src/components/Analytics/GAListener.tsx`), and `generate_lead` is GA4's own standard lead event — so the "Generate leads" business-objective collection lights up on its own. What it *cannot* do without registration is break leads down by form, by block or by originating kiosk: GA4 accepts unregistered parameters but will not offer them as dimensions. Register them (Admin → Custom definitions, event scope) and the board becomes leads-per-form, leads-per-block and claims-per-machine without touching code.

## Client Manual (final usage guide)

- **Hiding a layout block without deleting it** — set a block's "Block Name" (admin field, top of each block in the Layout list) to exactly `hidden` (case-insensitive, e.g. `Hidden`) and it stops rendering on the page while staying fully configured. Useful for sections still waiting on content that shouldn't block a release. A name that merely *contains* "hidden" (e.g. `Hidden promo (old)`) still renders — only an exact match toggles it off. Implemented in `src/blocks/RenderBlocks.tsx`.

## GDPR / Privacy Compliance

Audited 2026-07-19 — site did not comply, no consent mechanism existed at all. Implemented on `feat/gdpr-consent-banner`.

- **PII consent checkbox on lead-capture forms — live, but the copy is still wrong.** Code shipped on `feat/forms-hardening-and-ux`: a `requiresConsent` toggle plus localized `consentText` on the Form, and read-only `consentGiven`/`consentAt` on each submission, written by `/next/form-submissions` at the moment of capture. **Turned on in production later that same day (2026-07-30) — `requiresConsent: true` on all four forms**, confirmed against a fresh production dump (Design Your Kiosk, Contact, Placement Application, Start developing your kiosk). An earlier version of this entry said the opposite; it was written before the data pass happened.

  What is still outstanding is the **copy**, and it is worse than it looks: `Consent Text` had no toolbar until #193 (v1.38.1), so the privacy-policy link could not be inserted at all — and trying to insert one silently deleted the selected words. Form 9 shipped reading `See the  for how the data is handled.`, i.e. a live, required consent checkbox next to a sentence with the link words missing. Rewrite the consent copy on all four forms, in **both** locales, now that the toolbar exists.

  **How to turn it on — two sidebar fields, no form-builder field.** An earlier version of this entry said the checkbox was "an ordinary form-builder field named exactly `consent`, added by hand per form". That is wrong, and following it would leave a duplicate checkbox on every form. `FormBlock` renders the consent row itself whenever `requiresConsent` is on (`src/blocks/Form/Component.tsx`), registers it as `consent` with `required: true`, and adds that name to the declared-fields allowlist so the value survives into `submissionData` — which is what `/next/form-submissions` reads to write `consentGiven`/`consentAt`. So per form: tick **Requires consent**, then write **Consent text** in **both locales** (it is `localized`, and an empty ES falls back to generic wording rather than the copy you meant). Nothing else.

  Two consequences worth knowing before flipping it on four live lead forms: the checkbox is **required**, so it adds friction to every submission; and the Monday sync is unaffected — a submitted field with no `externalId` mapping is skipped silently (`syncFormSubmission.ts:90`), so `consent` simply never reaches the board, which is correct since the proof lives on the submission record. Verify with one test submission per form: the record should show `consentGiven: true` with a timestamp.

  Verified against a production dump: the migration leaves `consentGiven` NULL on pre-existing submissions, which is deliberate — backfilling `false` would assert that those people declined, and `true` would fabricate a consent that never happened.
- Not a gap: JotForm integration (`JotFormRepository`) is server-to-server (API calls), not a client embed — no extra third-party cookies from it. No other ad-tech/fingerprinting scripts found in a first pass.

## Launch checklist (WordPress decommission)

- **Scan a real QR code on a deployed kiosk** against a preview deploy before decommissioning WordPress — confirms the `machine_id` query param printed on physical kiosks still resolves correctly end to end. The QR encodes `/customer-service?machine_id=...` (the Support Hub landing page, not the refund form directly) — `SupportHub` (`src/blocks/SupportHub/Component.tsx`) reads `machine_id` off that page's own URL and forwards it onto the "Request a refund" link, so `ClaimForm` (a separate URL) still has it in its own `searchParams` when the customer arrives there. Full chain documented in `docs/superpowers/specs/2026-07-22-monday-claims-integration-design.md` § 5.
- **Check Neon's branch-expiration setting** (dashboard, or the Vercel↔Neon integration config) — confirm whether preview-deployment branches auto-delete on a timer and after how long, so nobody loses a staging branch they meant to keep using. **Now load-bearing:** `preview/latest` was created 2026-07-30 as the standing preview branch, kept level with `main` **on demand** (`git merge --ff-only main`, deliberately not automated — a preview build per merge to `main` is the cost that was cut on purpose), and its Neon branch was reset from production so migrations rehearse against real content. If those branches expire on a timer, that whole setup disappears quietly.
