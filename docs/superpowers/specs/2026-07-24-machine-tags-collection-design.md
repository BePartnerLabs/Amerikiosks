# Machine tags as a real collection — design

## Problem

Both `Machines.tags` and `FormatsGrid.filterTags` are free-text arrays (`{ label: text }[]` / `{ tag: text }[]`). Filtering matches by exact string (`'tags.label': { in: [...] }`), so a typo on either side silently breaks the filter with no error. There's no way to see which tags already exist while typing a new one.

## Goal

Let editors tag machines and filter `FormatsGrid` by those tags with a searchable, typo-proof picker, reusing Payload's native `relationship` field UI (removable pills, search-to-select, inline "create new") instead of hand-rolling a custom chip component.

## Decisions (from brainstorming)

- New `Tags` collection, same minimal shape as the existing `Categories` collection (`label` text field, `read: anyone`, rest `authenticated`). No `scope`/type field — Machines is the only consumer today; add scoping later if a second consumer shows up (YAGNI).
- `Machines.tags` and `FormatsGrid.filterTags` both become `{ type: 'relationship', relationTo: 'tags', hasMany: true }` — no custom React field component needed, Payload's built-in relationship UI already gives chips + autocomplete + create-inline.
- Existing tag data (16 rows across `machines_tags`, one per seeded machine — `full-size`, `campaign`, `compact`, `premium`, `venue-lobby`, `venue-waiting`, `venue-common`, `venue-multi`, `agency-campaign`, `agency-popup`, `agency-multi-venue`, `agency-screens`, `emerging-pilot`, `emerging-founder`, `emerging-multi`, `emerging-consignment`) is preserved: the migration creates one `Tags` doc per distinct existing label and relinks each `Machine` to the corresponding new tag id, then drops the old `machines_tags` table.
- Local dev DB was dumped before starting (`pg_restore` command given to the user) so this can be tried and rolled back if it doesn't feel right.

## Collection: `src/collections/Tags.ts`

```ts
export const Tags: CollectionConfig = {
  slug: 'tags',
  access: { create: authenticated, delete: authenticated, read: anyone, update: authenticated },
  admin: { useAsTitle: 'label' },
  fields: [{ name: 'label', type: 'text', required: true, unique: true }],
}
```

Registered in `payload.config.ts`'s `collections` array, alongside `Categories`.

## Field changes

- `src/collections/Machines/index.ts`: `tags` field becomes:
  ```ts
  { name: 'tags', type: 'relationship', relationTo: 'tags', hasMany: true,
    admin: { description: 'e.g. full-size, compact, campaign, premium — used for block-level filtering' } }
  ```
- `src/blocks/FormatsGrid/config.ts`: `filterTags` field becomes:
  ```ts
  { name: 'filterTags', type: 'relationship', relationTo: 'tags', hasMany: true,
    admin: { description: 'Show machines matching these tags. Leave empty to show all. Ignored if items are set.' } }
  ```
  (drops the nested `{ tag: text }` array shape entirely — it's now a flat array of tag IDs)

## Query change: `src/blocks/FormatsGrid/Server.tsx`

```ts
const tagIds = (filterTags ?? [])
  .map((t) => (typeof t === 'object' ? t.id : t))
  .filter(Boolean)

const result = await payload.find({
  collection: 'machines',
  ...(tagIds.length > 0 ? { where: { tags: { in: tagIds } } } : {}),
  depth: 1,
  overrideAccess: false,
  locale: locale as 'en' | 'es',
})
```

## Migration

Hand-written (not purely auto-generated), since it needs a data step between the schema changes:
1. `CREATE TABLE tags` (+ locales/versions tables as generated by `payload migrate:create` for the new collection).
2. Add `machines_rels`-style relationship column/junction for `Machines.tags` and `formats_grid` (+ `_blocks` variants) for `filterTags` (as generated).
3. Data step: `INSERT INTO tags (label, ...) SELECT DISTINCT label FROM machines_tags`, then insert into the new `machines_rels`-equivalent junction table joining each `machines_tags._parent_id` to the newly created tag id (matched by label), then `DROP TABLE machines_tags`.
4. Verify row counts match (16 in, 16 out) before finalizing.
